# T11 — M2b exit criterion 5: a first thermal result on real hardware

**Written:** 2026-10-20 22:12 UTC
**Milestone:** M2b (exit criterion 5, docs/IMPLEMENTATION.md §4)
**Status:** NOT MET. This record says why, and what to run where it can be met.

T11 is the manual tier: a result that only hardware can give, recorded by the person
who ran it. One file per occurrence, never overwritten; the next run adds another
named with its own date and time.

## What the criterion asks

"First meaningful thermal result recorded on real hardware": the temperature of the
machine under the dense-linear-algebra workload, against the machine idle, with the
run's verification clean, on a machine whose sensors LoadForge can read.

## This occurrence

Run in the development container of stream 11 (2026-10-20 22:12 UTC): a virtual machine, four vCPUs of
an Intel Xeon at 2.80 GHz, Linux 6.18.44, no hwmon chip, no thermal zone, no fan, no
cpufreq. `loadforge stress --test dense_linear` states it first, and it is the run's
own words:

```
  capabilities:
telemetry capability: 9 of 15 metric(s) present
  thermal: 0 of 1 present
    thermal.package (package 0): not offered by this kernel
      where:  /sys/class/hwmon
      why:    no hwmon chip with a temperature input and no thermal zone
  fan: 0 of 1 present
    fan.speed (device 0): not offered by this kernel
  frequency: 2 of 6 present
    frequency.cpu x4: not offered by this kernel
      where:  /sys/devices/system/cpu/cpu0/cpufreq/scaling_cur_freq
  memory: 7 of 7 present
```

A temperature cannot be read here, so no thermal result exists to record. A number
taken from anywhere else (the host's, a guess, a published figure) would be the
fabricated fact the project's tooling is built to refuse, so none is given.
What this occurrence does establish is the other half of the criterion: the dense
linear workload runs on the AVX2 path under supervision, every unit is checked by its
independent oracle over sampled entries and none is found wrong (see
docs/journal/11-integration-m2.md and the `cli_stress_test_dense_linear` test).

## The procedure for a machine that can give the result

1. Build a release binary (`cmake --preset release`), and note `loadforge --version`
   and `git rev-parse HEAD`.
2. Idle: for two minutes record every temperature the machine offers, once a second.
   `for f in /sys/class/hwmon/hwmon*/temp*_input /sys/class/thermal/thermal_zone*/temp;
   do echo "$f $(cat $f)"; done` in a loop with `date -u +%s` is enough; the
   sampler that does it inside LoadForge is M3's.
3. Under load: `loadforge stress --test dense_linear --duration 10m`, saving its whole
   output, while the same recorder runs. The banner's capability report must list a
   thermal metric as present; if it says absent, the machine cannot give this result.
4. Idle again for two minutes.
5. Record here, in a new file named `m2b-thermal-<date>-<time>-UTC.md`: the machine
   (CPU model, cooling, ambient if known), the build, the three recordings' minimum,
   median and maximum, the run's exit code and its verification line per worker
   ("the oracle checked N of them over B sampled block(s) and found W wrong"), and
   whether the load raised the temperature beyond the idle spread. A verification line
   that reports a wrong result is itself the result and is reported as one.

Do the same on an AArch64 machine; M7's manual checklist repeats it across machines.
