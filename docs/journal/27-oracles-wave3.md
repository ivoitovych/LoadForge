# Journal fragment 27 — the wave-3 oracles: FFT, stencil, sparse, graph, particles

**Written:** 2026-10-20 17:45 UTC
**Change:** `src/verification/oracle/{fft,stencil,sparse,graph,particles}/`, their
tests in the unit, oracle and fault-injection tiers, their real-tool fixtures,
and five ledger fragments. Each oracle is written from its specification
header (`src/workloads/<name>/spec.hpp`) and from nothing else; no workload
code was read, and none exists in the tree yet.

## Established by experiment

### The real tools sit far inside the derived tolerances, except where the bound is not the limit

Each fixture was made by a tool that is not the specification's algorithm, and
the oracles accept all of them. The margin, measured as worst residual over
tolerance at every bin, cell, row or sampled entry (not only the sampled ones),
with the reference recomputed in long double where the tool is the thing being
checked:

| Oracle | Tool | Worst residual / T' |
|---|---|---|
| FFT | `numpy.fft.fft` (radix 4 tolerance) | bins 1.0e-5, Parseval 7.3e-5 (T'_bin about 4.7e-9 for ‖x‖ ≈ 52) |
| stencil | `scipy.ndimage.correlate`, ring restored | 1.6e-2 (T' = 7.1e-15) |
| sparse | `scipy.sparse.linalg.cg`, 16 iterations | ‖r‖/‖b‖ = 2.2e-16 against a bound of 1.97e-11: held by 8.9e4 — the specification's own measurement ("about 10^5") reproduced |
| particles | `scipy.spatial.cKDTree` + numpy sum | 4.3e-3 |
| graph | `scipy.sparse.csgraph.dijkstra` (distances) | exact, no margin |

So the bounds are not hair-triggers on healthy output: the nearest to its limit
is the stencil at 1.6 %, where eight sweeps of five rounded terms are all the
tolerance has to cover.

### Parseval's residual cannot be placed at (1 ± 2^-20) of its tolerance

The specification asks every bounded oracle's tolerance to be tested at
(1 + ε) T' and (1 − ε) T', ε = 2^-20. For the FFT's Parseval check the residual
is `|s^ − 64 a^|`, a difference of two doubles near 64 (or near 64‖x‖ for any
input), so it moves in steps of one ulp of that magnitude, 2^-47 near 64.
T_parseval is about 64 × 1.8e-12 = 1.2e-10, so the step is about 2^-13 of the
tolerance: no output has a residual within 2^-20 of the limit. The scale of the
input does not help (both numbers scale together). The test finds, by
bisection on the offset of one bin, the nearest representable residual on each
side of (1 ± 2^-20) T', requires both to be on the right side, and requires the
held one to be within 2^-11 of the limit. The bin check, the stencil, the sparse
rows and norm and the particles all reach ε exactly, by arranging for the exact
residual to be zero (an imaginary part, a lone cell far from every window, a
cancelling row, a symmetric cluster) so that the offset *is* the residual.

### An unreduced angle cannot check a twiddle table near its zeros

The first test of the FFT's table against the C library's `long double` sine
and cosine took `cosl(2π m / n)` directly and failed 23 of 8192 entries — every
one near a zero of the function, where a relative error of 2^-64 in the angle is
a large share of a tiny value (`cos` at m = 1024 came out 2.5e-20, not 0). The
test reduces the angle to [0, π/4] by exact integer arithmetic first (quadrant
and reflection), and then every entry is within half a spacing of the true value
with 1 % to spare. It cannot prove round-to-nearest for an entry whose true value
is within 2^-11 of a midpoint (long double has 11 more bits than double); the
table is generated by exact rational rounding of a 100-digit value, and the
generator is committed beside the fixtures.

### gcov counts go negative under threads, and atomic counters are expensive in a hot loop

As the brief warned, `OracleContract`'s concurrent test gave a negative branch
count (`branch 8 taken -350`) until the oracle targets got
`-fprofile-update=atomic` in the coverage build. The price is real: one graph
check took 1.5 s under the coverage preset against 0.1 s in the plain debug
build, and the first version of the graph oracle, which decoded each head with a
four-iteration byte loop at every one of 4.7 million uses, ran the oracle tier
past eleven CPU-minutes because the contract suite runs five checks at once on
the same counters. The heads are now decoded once into the scratch (one pass of
262144) and the sixteen PageRank sweeps read a plain array.

### The contract suites are instantiated where they are declared

`INSTANTIATE_TYPED_TEST_SUITE_P(Prefix, contracts::OracleContract, ...)` does
not compile: the macro pastes the suite name into identifiers it expects in the
current namespace (`gtest_typed_test_suite_p_state_<Suite>_`). The oracle tests
therefore close their own namespace and open `loadforge::contracts` for the
subject types and the instantiation, as the reference tests in
`tests/contracts/` do. The registry suite in the same header is allowed
uninstantiated, as wave 2 found.

### A sample shared between two units is a birthday collision, not a defect

The particles oracle's sample is fixed by one number in [0, 4094), so among
3000 consecutive unit indices about 2100 distinct samples appear. The first
version of the test demanded 2990 and was wrong; the FFT's, set by two
independent numbers in [0, 2047), shows essentially none shared.

## Decisions

### D1. Allocation: none where it can be avoided; a factory where it cannot

Options: catch `std::bad_alloc`; scratch as a member; thread-local scratch;
stack. The FFT (64 KiB of decoded input), stencil (two 9 KiB buffers), sparse
(nothing — one row at a time) and particles (96 KiB of decoded positions) fit
on the stack and allocate nothing, so `NotChecked` for a failed allocation does
not arise. The graph oracle recomputes its whole output (4 MiB), takes it from
a `ScratchFactory` function pointer, and answers `NotChecked` when the factory
returns nothing; the factory is the injection seam. The reasoning and the
rejected options are in `docs/adr/proposed/27-oracles-scratch-and-sampling.md`.

### D2. The sample of a unit is arithmetic on a mixed index, with the pinned members written in

FFT: bins 0 and 2048 plus seven in each open half of the spectrum, each half a
progression with stride 293 modulo 2047 from an offset the index fixes. Particles:
0 and 4095 plus fourteen from a progression with stride 293 modulo 4094. Stencil:
the two corner windows, then two whose origins are the index mixed with four
salts, modulo 241. The mix is the splitmix64 finaliser. A progression with a
stride coprime to the modulus visits distinct values, so there is no rejection
loop and no branch that a particular index would be needed to reach.

### D3. The oracle's table for the FFT is a copy generated from the definition

The specification defines W[m] as a function of n and says the workload's table
is generated offline. The oracle holds its own, all 4096 entries, produced by
`tests/fixtures/verification/oracle/fft/generate_twiddles.py` (mpmath at 100
digits, exact rational rounding, the multiples of n/4 written down) rather than
derived from a first-octant table at run time. Options: octant reduction in the
oracle (a third of the data, more code to cover and to get wrong); libm (not
reproducible, determinism.md §4). A flat table has one accessor and is checked
for the exact images the specification names, for every m.

### D4. A plan is held to the specification even where the oracle does not depend on it

The stencil, sparse and particles oracles do not use the plan's decomposition
(tile edge, chunk rows, cells per cutoff): what they check does not change with
it. `create()` still refuses a decomposition that is not one of the
specification's, as `OracleFault::kConfiguration` — "a decomposition it does not
have" (`oracle.hpp`) — rather than accept any value: an oracle created for a
plan the workload could not have resolved is a wiring mistake the registry
should see at once. The FFT and graph oracles use it (radix, accumulators).

### D5. The graph oracle accumulates by walking the edges; the model gathers per vertex

The specification states PageRank as a per-vertex gather over the in-edges in
increasing edge number, term q to accumulator q mod a. The oracle reaches the
same additions in the same order by walking the edges in increasing order,
adding each term into the accumulator `slot[edge]` of its head's row, where the
slot is the edge's rank among its head's in-edges modulo a. Every accumulator
receives its terms in increasing q, and the combination S is the left-to-right
sum of the accumulators. This avoids building in-edge lists (a counting sort and
1 MiB more). The test model (`graph_evidence.hpp`) is the literal gather over
explicit in-edge lists, so the two are different programs; they agree to the bit
on five shapes of graph (generated, one vertex, self-loops, a ring with chords,
numbers beyond V) at every accumulator count, and both agree with the Python
model that wrote the ranks fixture.

### D6. The tolerance tests mirror the oracle's evaluation order, once, where epsilon needs it

The sparse row test sets the reported residual to `r~_i + (1 ± ε) T'` where
`r~_i` is the oracle's own plain-order residual. For the offset to be the
residual to better than 2^-20 of T', the test's `r~_i` must equal the oracle's
bit for bit, so `evidence::explicit_residual` forms it in the same order (b,
then the entries by increasing column, one multiplication and one subtraction
each, `-ffp-contract=off`). The specification allows any fixed order; this is
the test choosing the oracle's. Nothing else mirrors it: the particles tests use
the oracle's own `direct_force` for the base value only where the force is
verified small (≤ 1e-7) so its ulp is far below ε T', and the long-double
evaluation in the unit tier checks `direct_force` itself independently.

### D7. Fixtures hold what the real tool made; inputs are regenerated

Each fixture is the output of numpy, scipy, or (for the graph's PageRank bits,
which no library produces) a Python model of the specification's text, with the
command, the versions and the machine in the generating script's docstring. The
inputs are not committed (they would be 64 KiB to 1 MiB each): the tests
regenerate them with the contract's `philox.hpp`, and the Python generators
carry their own Philox, checked against Random123's published vectors every
time they run (`philox_reference.py`). A disagreement between the two Philox
implementations would show as a failed agreement in the T3 tests, which is the
check that the Python input and the C++ input are the same bytes. The graph's
PageRank model is additionally checked against scipy's power iteration to 1e-13
relative inside its generator, so an error in its graph, damping or iteration
count shows.

### D8. Three readings meet for the graph

The ranks fixture (Python), the test model (C++ gather) and the oracle (C++
edge walk) are three programs written from the same text. The oracle is
refused for every accumulator count but its own on the fixture of another, which
shows the order of the sums is part of what the exact contract pins.

## Contract questions

1. **FFT, §5 of the specification: the (1 ± 2^-20) test for Parseval cannot be
   met as written** (see "Established by experiment"). Reading taken: the
   nearest representable residual on each side, within 2^-11 of the limit. The
   specification's sentence could say "for the dft-bin check and, for
   Parseval, at the nearest residuals either side".

2. **Graph: `NotChecked` "Nothing else".** The specification says the only way
   the graph oracle returns `NotChecked` is evidence of the wrong size; `oracle.hpp`
   lists a scratch allocation that failed. Reading taken: both; the oracle needs
   4 MiB and cannot honestly answer anything but `NotChecked` when it has none.

3. **Sparse, the input checks versus "stops at the first that fails".** The
   specification orders the n + 1 checks and says to stop at the first failure,
   and separately lists the inputs for which the verdict is `NotChecked`. Reading
   taken: every `NotChecked` condition is decided before any check is made
   (the whole structure, every value and b are read first), so a bad input is never
   reported as a row mismatch. `row_ptr` is validated as: starts at zero, and each
   row's length is the fixed length — which fixes every pointer.

4. **Particles, `-0.0`.** "Any input coordinate … outside [0, kBoxEdge)" is
   `NotChecked`. `-0.0` is numerically inside the interval; the oracle accepts it
   (the generator never writes it, and the tolerance derivation does not care).
   Likewise `-1.0` for the FFT, stencil and sparse right-hand side is accepted
   as the generator can reach it (`entry_value(0) == -1.0`).

5. **Particles, candidates versus terms.** M_p counts every j with q~ < the
   candidate limit, including pairs with q between 4 and the limit and pairs on
   top of the particle, whose terms are exactly zero. The bound is stated for
   that M_p, and so is the implementation; the tests pin the counting at q = 4,
   between 4 and the limit, and beyond it.

6. **`OracleContract::wrong()` for a sampling oracle.** The contract asks for
   corruptions "caught whatever the oracle samples". The FFT can meet that
   (Parseval sees any large error anywhere); the particles and stencil oracles
   examine only their samples, so no corruption at one entry is caught whatever
   the sample is. Reading taken, as the contract's own parenthesis allows:
   corruptions in the blocks the unit's index samples (found through the
   oracle's public `sampled_particles` / `window_origins`), plus, for particles,
   the sign of every entry.

7. **Descriptor.determinism is not an oracle input.** Nothing here reads
   `WorkloadConfig`; `create()` takes the plan only. If the integration stream
   expects the oracle to see the ISA path, the contract would need to say so.
